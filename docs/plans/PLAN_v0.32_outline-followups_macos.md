## 1. 문제

QuickTalk 대화 창은 기본 400×560, 최소 380×420 이다. 질문·답이 10번만 오가도 한 화면에 한두 쌍만 남는다.
지금은 **스크롤로만** 과거 질문을 찾을 수 있고, 보관함 검색은 **대화 단위**라 "그 대화의 세 번째 질문"으로는 갈 수 없다.

> 사용자 요청 — *"짧은 대화는 스크롤을 사용할 수 있지만 긴 대화 그러니까 질답이 많은 대화는 어려움이 있음"*

두 가지를 제안한다.

1. **대화 목차** — 이 대화의 질문만 모아 보여 주고, 클릭하면 그 자리로 이동.
2. **후속 질문 제안** — 응답이 끝나면 YouTube·Gemini 처럼 이어질 질문 3개를 칩으로 보여 주고, 클릭하면 바로 이어서 묻는다.

둘 다 **설정 › 대화**에서 각각 켜고 끈다.

## 2. 요구사항

| ID | 요구 |
| --- | --- |
| R1 | 질문 목록에서 클릭 한 번으로 그 질문으로 이동(스크롤 애니메이션 + 잠깐 강조) |
| R2 | 400×560 기본 창에서 대화를 **상시 가리지 않는다**. 380×420 에서도 표현이 무너지지 않는다 |
| R3 | 응답이 끝나면 후속 질문 2~4개(기본 3)를 그 답변 아래에 보여 준다 |
| R4 | 설정 › 대화 에서 목차 표시 방식과 후속 질문을 각각 켜고 끈다 |
| R5 | 한국어·English 동시 제공(앱 규칙), 답변 언어를 따라간다 |
| R6 | 키보드·VoiceOver·동작 줄이기(Reduce Motion) 대응 |
| R7 | 모델 호출이 응답을 방해하지 않는다(비용·지연·동시성) |

## 3. 참고 구현 조사 (LiteRT-LM-Studio)

### 3.1 대화 목차 — `ChatOutlineView` + `ChatPaneView`

- 대화창 **오른쪽 중앙**에 3줄 손잡이. 호버하면 패널이 펼쳐진다(최대 폭 220, 최대 높이 400).
- 목록은 **사용자 메시지만**, 각 항목은 첫 줄 **40자**(빈 본문은 "이미지").
- 펼칠 때 **마지막 질문이 보이도록** 스크롤, 항목 클릭 시 1.5초 플래시 + 스크롤.
- 설정 스위치 `chatOutlineEnabled` **기본 ON**.

### 3.2 후속 질문 — `FollowUpSuggest` + `FollowUpChipsView`

- **마지막 정상 응답에만** 표시. 스트리밍 중·오류 응답에는 없음.
- LLM 생성: 유휴 **3초** 뒤 1회, 질문 600자/답변 500자 프롬프트, `max 64 tokens`.
- 실패 시 **휴리스틱 폴백**(응답 키워드 기반 3~4개). 스켈레톤 최소 0.4초, 칩 클릭 = 즉시 전송.
- 설정 스위치 `followUpEnabled` **기본 ON**.

### 3.3 가져올 것 / 버릴 것

| 참고 구현 | QuickTalk 결정 |
| --- | --- |
| 3줄 손잡이 | **미니맵 눈금**으로 바꾼다 — 질문 개수와 현재 위치가 한눈에 보인다(폭은 22pt 그대로) |
| 폭 220 / 높이 400 고정 | 창 크기에 맞춰 **폭 55%·높이 −200pt** 로 클램프(380×420 → 208×220) |
| 펼칠 때 마지막 질문으로 | **현재 읽고 있는 질문**이 보이게(다르면 그쪽으로) |
| 클릭 1.5초 플래시 | 기존 `focusTurn` 재사용(이미 3회 스크롤 + 펄스 구현됨) |
| 유휴 3초 생성 | **2.5초** + 8초 타임아웃 + 응답 중이면 skip(모델 슬롯 보호) |
| 휴리스틱 폴백 | 그대로 채택. 단 폴백도 **답변 언어**를 따른다 |

## 4. 1안 vs 2안

### 1안 — 대화창 오른쪽 중앙 플로팅 레일 (참고 프로젝트 방식)

- **장점**: 대화를 보면서 바로 쓴다. 시선 이동 0. 긴 대화에서 "지금 어디쯤인지"가 항상 보인다. 창을 전환하지 않는다.
- **단점**: 좁은 창에서 펼친 패널이 본문을 덮는다(400폭의 55%). 처음에는 손잡이의 용도를 모를 수 있다.

### 2안 — QuickShelf(⌥⇧V) 대화 탭에 목차

- **장점**: 이미 있는 목록 UI를 재사용해 구현이 가장 싸다. "대화 목록 + 그 대화의 질문"이 한 곳에 모인다. 폭 320이라 질문이 덜 잘린다.
- **단점**: **대화를 보면서 쓸 수 없다**. 셸프를 열면 대화창 조작이 끊기고, 점프 후 셸프를 닫는 두 동작이 필요하다. 긴 대화에서 "읽다가 잠깐 점프"하는 흐름에 맞지 않는다.

### 비교

| 기준 | 1안 플로팅 레일 | 2안 QuickShelf |
| --- | --- | --- |
| 대화 보면서 사용 | ✅ 항상 | ❌ 셸프를 열고 닫아야 |
| 발견성 | 보통(손잡이를 알아야) | 좋음(대화 탭 안) |
| 작은 창 400×560 | 펼칠 때 55% 덮음(일시적) | 창 밖 별도 패널 |
| 긴 질문 가독성 | 40자에서 잘림 | 폭 320으로 덜 잘림 |
| 현재 위치 표시 | ✅ 레일 눈금 | ✅ "지금" 표시 |
| 구현 비용 | 중(오버레이·호버·위치 추적) | 낮음(기존 목록 재사용) |
| 다중 대화 | 방마다 자기 목차 | 셸프에서 방 전환과 함께 |
| 기록/검색과 관계 | 대화 내 이동만 | 대화 목록·검색과 같은 곳 |

### 권장 — 하이브리드

> **기본은 1안(플로팅 레일), 2안은 보조 진입.**
> 같은 `ConversationOutline` 모델을 공유하므로 QuickShelf 쪽은 "목록을 한 번 더 그리는" 비용만 든다.
> 설정에서 `끔 / 플로팅 레일 / 퀵셸프 / 둘 다` 를 고를 수 있게 해, 1안이 좁은 창에서 불편하면 2안으로 내릴 수 있게 한다.

## 5. 최종 제안 — 화면 명세

### 5.1 접힌 레일 (평상시)

```
        ┌ 대화 영역 ─────────────────┐  ┌─┐
        │  질문 …                     │  │•│  ← 눈금 12개
        │  답변 …                     │  │•│     현재 위치는 보라색 막대
        │  질문 …                     │  │▮│
        └────────────────────────────┘  └─┘
```

- 폭 22pt, 높이 ≈ 질문 수 × 6pt(최대 92). 오른쪽에서 6pt.
- 질문 수만큼 2×2 눈금, **현재 질문은 4×12 보라색 막대**.
- 도구 설명(`.help`) "대화 목차 — 마우스를 올려 펼치기".
- **질문이 2개 이하면 표시하지 않는다**(가치 없음 + 노이즈).

### 5.2 펼친 패널

- 폭 `min(216, 창폭 × 0.55)` · 높이 `min(300, 창높이 − 200)`.
- 머리말: "대화 목차" + `12개` 배지.
- 8개 이상이면 **질문 검색** 입력줄(부분 일치, 대소문자 무시).
- 목록: 질문 첫 줄 40자, 1줄 고정, 현재 항목은 보라 배경 + 굵게.
- 바닥: "클릭하면 그 질문으로 이동" + `아래 2개 더`(잘린 개수).
- **여는 규칙**: 호버 0.35초 → 펼침. 레일 클릭 → 즉시 펼침 + 고정. 바깥 클릭·Esc·스크롤·전송 → 접힘.
- **펼친 패널은 오버레이**다. 본문 폭을 줄이면 400pt 창에서 글자가 5자마다 끊긴다(목업에서 확인). 잠깐 덮는 편이 낫다.
- 항목 클릭 → `focusTurn`(기존 경로) → 3회 재스크롤 + 1.5초 펄스 → 패널 접힘.

### 5.3 현재 위치 계산

- 각 턴에 `.id(turn.id)` 가 이미 있으므로, 동일 `coordinateSpace` 기준 `PreferenceKey`로 턴별 y를 모은다.
- `ScrollOffsetObserver` 가 주는 오프셋과 비교해 **화면 상단에 가장 가까운 질문**을 현재로 정한다.
- 갱신은 스크롤 중 0.1초 스로틀(질문 50개에서도 O(n) 1회).

### 5.4 좁은 창 대응 (380×420)

| | 400×560 | 380×420 |
| --- | --- | --- |
| 레일 | 22×92 | 22×92 |
| 패널 폭 | 216 (54%) | 208 (55%) |
| 패널 높이 | 300 (54%) | 220 (52%) |
| 보이는 질문 | 9개 | 5개 |
| 본문 우측 여백 | 30pt 고정 (레일 28pt + 2pt 여유) | 동일 |

`docs/qa/v0.32-outline-followups/outline-narrow-ko.png` 에서 확인.

### 5.5 키보드 · 접근성

- 목차 열기 `⌥⌘O`(후보 — 기존 단축키와 충돌 확인 후 확정), `↑`/`↓` 이동, `Return` 점프, `Esc` 닫기.
- VoiceOver: 각 행 `"질문 3/12, 리포트가 아직 없는 이유는?"`, 레일은 `"대화 목차, 질문 12개, 현재 8번째"`.
- 동작 줄이기: 펄스 반복 생략, 패널 페이드만 유지.
- 다크·라이트 모두 `ultraThinMaterial` + 8% 흰 테두리(기존 QuickShelf와 같은 결).

### 5.6 QuickShelf 보조 진입

- 대화 탭 최상단에 접이식 **"이 대화 목차 (12)"** — 최근 6개 + "6개 더 보기".
- 현재 질문에 "지금" 배지. 클릭하면 **셸프를 닫고** 그 질문으로 점프.
- `docs/qa/v0.32-outline-followups/shelf-outline-ko.png`.

## 6. 후속 질문 명세

### 6.1 언제 만드나

| 조건 | 처리 |
| --- | --- |
| 설정 OFF | 아무것도 하지 않음 |
| 응답 정상 종료 + 답변 80자 이상 | 대상 |
| 오류·중단·취소·빈 응답 | 표시 안 함 |
| 답변이 짧음(<80자) | 표시 안 함(칩이 답변보다 커진다) |
| 마지막 턴이 아님(과거 스크롤) | **캐시가 있으면 표시**, 없으면 생성하지 않음 |
| 새 질문 전송·입력 시작 | 예약 취소 |
| 2.5초 유휴 | 그때 1회 생성 시작 |

### 6.2 어떻게 만드나

1. **모델 생성(기본)** — 현재 제공자로 비스트리밍 1회.
   - 프롬프트: 질문 600자 + 답변 500자 + "같은 언어로, 12자~24자, 3개, 번호만".
   - `max 64 tokens` 상당, **8초 타임아웃**, 실패·빈 응답이면 폴백.
   - `UIStore.reply(provider:prompt:history:attachments:)` 재사용(새 클라이언트 없음).
2. **무료 문구** — 답변 키워드 기반 휴리스틱 3개(예: "예시로 보여줘", "더 자세히", "다음 단계는?"). 모델 호출 0.

### 6.3 어떻게 보이나

- 답변 아래 **우측 정렬 칩 3개**, 위에 작은 라벨 `✦ 이어서 물어보기`.
- 생성 중에는 스켈레톤 0.3초(그 사이 끝나면 바로 칩).
- 칩 클릭 → 즉시 전송(설정 OFF면 입력창에 넣기만).
- 응답이 시작되면 칩은 사라지고, 그 응답이 끝나면 새 칩으로 교체.
- **답변 말풍선 안이 아니라 아래**에 둔다 — 복사·읽어주기 메타 줄과 섞이지 않게.

### 6.4 저장·캐시

- 키: `대화 ID + 턴 ID`. 메모리에만 보관, 앱 재실행 시 사라짐(기록 파일에 쓰지 않는다).
- 이유: ① 기록 용량·프라이버시 ② 모델·설정이 바뀌면 다시 만드는 게 자연스럽다 ③ 실패해도 기록이 오염되지 않는다.
- 스크롤로 다시 올라오면 캐시로 즉시 표시.

### 6.5 모델 경합 방지

- Ollama 병렬 슬롯 1개, Apple FM 한도 → **응답 중이면 생성하지 않는다**.
- 생성 중 새 질문이 오면 **즉시 취소**(Task cancel + 결과 폐기).
- 예약 실행·예약 승인 대기 중에도 만들지 않는다.

**원인(실측·코드 추적)**

`focusTurn` 이 `focusedTurn` 만 세우고 `followsBottom` 은 건드리지 않았다. 점프로 스크롤 오프셋이 바뀌면 `ScrollOffsetObserver` 가 `(distance, didScrollUp)` 을 보고하는데, ① 점프가 아래 방향이거나 ② 레이아웃 확정 전 `distance` 가 잠깐 0 으로 보고되면 `handleScrollDistance` 가 `followsBottom = true` 로 되살렸고, 이후 중간에서 스크롤을 내리면 `guard followsBottom` 경로가 `pinBottom()` 을 호출해 맨 아래로 붙였다. 스크롤 알림은 초당 수십 번 오므로 타이밍에 따라 "가끔"으로 보였다.

**수정 규칙(테스트로 고정)**

- 프로그램 이동 시작 → `followsBottom = false`, `atBottom = false`, `suppressUntil = now + 1.0s`.
- 억제 중에는 `atEnd` 가 true 로 보고돼도 따라가기를 **되살리지 않고** 핀도 보내지 않는다.
- 억제가 끝난 뒤 사용자가 직접 바닥에 닿으면(`distance ≤ 24`) 다시 따라간다.
- 명시적 `jumpToBottom()`(새 질문·맨 아래 버튼·승인 카드)은 억제를 해제한다.
